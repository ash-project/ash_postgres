# Temporal Resources

Temporal resources keep every version of every record, each valid for a period of time.
How to define and use them is covered in Ash's
[temporal resources guide](https://hexdocs.pm/ash/temporal-resources.html). This page covers
what AshPostgres needs and does for them.

## Requirements

Temporal resources need **PostgreSQL 18 or later**, and the repo has to say so:

```elixir
def min_pg_version do
  %Version{major: 18, minor: 0, patch: 0}
end
```

They also need the `btree_gist` extension, because the temporal primary key is backed by a
GiST exclusion constraint:

```elixir
def installed_extensions do
  ["ash-functions", "btree_gist"]
end
```

A temporal resource whose repo doesn't declare both fails to compile.

## What the migration generator creates

For a temporal resource, `mix ash_postgres.generate_migrations` creates:

- the period column, a `tstzrange`
- `PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)`, so a record can have many versions, but never
  two valid at the same time
- `PERIOD` foreign keys for relationships between temporal resources
- identities as exclusion constraints, so they're unique at every instant rather than across
  all of time

## How writes split versions

A write at an instant changes only the part of each version from that instant onward, and
keeps the rest as it was. SQL:2011 calls this `UPDATE/DELETE ... FOR PORTION OF`.

That was planned for PostgreSQL 19, but it was reverted before release, because concurrent
writes under `READ COMMITTED` could silently lose part of an update. So AshPostgres splits
versions itself, in a single statement: it writes the slice the write covers, and puts back
the rest of the version as new rows. Once PostgreSQL ships `FOR PORTION OF` natively,
AshPostgres will use it.

## Concurrent writes

Under `READ COMMITTED`, each temporal write locks the versions it's about to split, and checks
that they're the versions it expected. If another transaction changed one of them in the
meantime, the write does nothing and runs again, holding the locks it already took. Two upserts
that race to create the same record are retried the same way.

After 25 conflicts in a row, which takes many transactions writing the same slice of the same
record at once, the action fails with `AshPostgres.Temporal.WriteConflict`. Nothing was
written, so retrying it is safe.

Under `REPEATABLE READ` or `SERIALIZABLE`, PostgreSQL raises a serialization failure for these
cases itself, and retrying is up to you.

## Upgrading from earlier versions

Migrations generated by earlier versions of AshPostgres only created the temporal primary key,
temporal identities and `PERIOD` foreign keys on PostgreSQL 19, and fell back to plain keys
otherwise. If you ran them on PostgreSQL 18, your tables have the plain keys. Check with:

```sql
SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'your_table'::regclass;
```

If the primary key doesn't include `WITHOUT OVERLAPS`, write a migration that drops it and
adds `PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)`, and do the same for identities and
`PERIOD` foreign keys.
